Question 1: Scale (5 Marks)

1(a). Peak-Demand Scenario & High-Availability Cluster Ingress

Peak-Demand Scenario (Exam Week 08:00 AM Desk Rush): During semester examination weeks, library management opens online seat reservations at 08:00:00 AM sharp for same-day quiet carrels, power-outlet desks, and collaborative rooms across Floors 1 to 4. Over 2,500 active university students concurrently refresh the portal within a 60-second window to claim scarce corner desks and quiet research cubicles.

Hardest-Hit API Identified: GET /api/spaces/:spaceId/seats. This endpoint is heavily read-intensive, performing real-time queries against table inventories (seats) joined with active reservation locks (reservations). Unmitigated, this endpoint causes thread-pool exhaustion and 504 Gateway Timeouts under sudden traffic spikes.

Containerized Cluster Setup: An Nginx reverse proxy load balancer routes traffic across 3 independent, containerized backend instances:

  • studyspace-nginx: Port 8000:80 (Load balancer entrypoint)
  • studyspace-backend-1: Port 5001:5000 (Container Node.js instance 1)
  • studyspace-backend-2: Port 5002:5000 (Container Node.js instance 2)
  • studyspace-backend-3: Port 5003:5000 (Container Node.js instance 3)
  • Neon Serverless DB: Cloud PostgreSQL instance over SSL/TLS (Ports 443 & 5432)

Live Round-Robin Distribution Verification: Each backend container injects the X-Backend-Instance header. Successive requests to http://localhost:8000/api/health cycle sequentially across all nodes:

Request 1 -> X-Backend-Instance: backend-2
Request 2 -> X-Backend-Instance: backend-3
Request 3 -> X-Backend-Instance: backend-1
Request 4 -> X-Backend-Instance: backend-2
Request 5 -> X-Backend-Instance: backend-3
Request 6 -> X-Backend-Instance: backend-1
[Verified: 1:1:1 Cyclic Round-Robin Dispatching without Session Sticking]

High availability mandates zero dropped connections when an application node fails. Using benchmarks/failover-test.js, traffic was continuously dispatched at $C=10$ while container studyspace-backend-2 was abruptly stopped mid-flight at timestamp $T = 3.0\text{ seconds}$.

Nginx Resilience Configuration (nginx/nginx.conf):

upstream backend_cluster {
    server backend-1:5000 max_fails=3 fail_timeout=10s;
    server backend-2:5000 max_fails=3 fail_timeout=10s;
    server backend-3:5000 max_fails=3 fail_timeout=10s;
}

server {
    listen 80;
    location / {
        proxy_pass http://backend_cluster;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # Automatic Failover & Retry Configuration (Question 1c)
        proxy_next_upstream error timeout invalid_header http_500 http_502 http_503 http_504;
        proxy_next_upstream_tries 3;
        proxy_next_upstream_timeout 10s;
        proxy_connect_timeout 1s;
        proxy_read_timeout 5s;
        proxy_send_timeout 5s;
    }
}

1(d). Comprehensive Cloud Architecture Diagram with Cloud Bursting

The production cloud topology implements tiered caching, reverse proxy load balancing, and automated edge cloud bursting:

Cloud Bursting & Edge Computing Architecture:

  • Edge Computing Component (Cloudflare Edge Cache): Short TTL (15s) caching absorbs over 80% of identical read requests during the 08:00 AM rush at regional PoPs before reaching the origin load balancer.
  • Cloud Bursting Trigger: If on-premise cluster CPU load exceeds 80% or origin response time exceeds 500ms, the DNS router spills surplus traffic into elastic serverless functions (AWS Lambda) connected to Neon's pooler.

Question 2: Secure (5 Marks)

2(a). Sensitive University Records & Salted Bcrypt Hashing

Identified Sensitive Student Records:

  • Personally Identifiable Information (PII): Student legal name, institutional email address (@vit.ac.in), contact details, and student roll number.
  • Physical Presence & Behavioral Data: Reservation history, timestamped desk occupancy, preferred study zones, and library check-in verifications.
  • Security Credentials: Passwords and dynamic TOTP two-factor secret keys.

Cryptographic Implementation (Bcrypt): Passwords undergo irreversible one-way salted hashing via bcryptjs using a cost factor of 10 ($2^{10} = 1024$ key expansion rounds). Plaintext passwords are never persisted to disk or log sinks: 

const saltRounds = 10;
const passwordHash = await bcrypt.hash(plaintextPassword, saltRounds);

2(b). Multi-Factor Authentication (TOTP) & Role-Based Access Control (RBAC)

1. RFC 6238 TOTP Multi-Factor Authentication:

  • Secret Generation (POST /api/auth/2fa/generate): Returns a cryptographic Base32 secret (GNY25CBIFNXCS6JRRTHCE765QCJEH6U4) and an otpauth:// QR code.
  • Activation (POST /api/auth/2fa/verify): Student scans into Google/Microsoft Authenticator and validates with 6-digit dynamic code 560604.
  • Login Challenge (POST /api/auth/login): If 2FA is active, login requests without TOTP are rejected with requires2FA: true. Valid TOTP issuance yields the signed JWT.

2. Role-Based Access Control (RBAC) Enforcement:

// 1. Unauthenticated Request (Missing JWT Token)
POST /api/spaces/1/seats -> HTTP 401 Unauthorized
Payload: {"error": "Access denied. No authentication token provided."}

// 2. Privilege Escalation Prevention (Student Token accessing Admin Route)
POST /api/spaces/1/seats [Bearer student_token] -> HTTP 403 Forbidden
Payload: {"error": "Forbidden. Admin privileges required."}

// 3. Authorized Administrator Request
POST /api/auth/login [admin@studyspace.com] -> HTTP 200 OK (Issued role: 'admin')

2(d). Domain Threat Agents & Regulatory Compliance Analysis

1. Higher Education Campus Threat Agents:

  • Threat Agent 1 (Rogue Student Scalper Bot): Automated scripts attempting to scalp all window desks at 08:00 AM. Mitigated via TOTP MFA, request rate-limiting, and SQL reservation overlap locks.
  • Threat Agent 2 (External Credential Stuffer): Attackers using leaked university password lists. Mitigated via 10-round salted bcrypt hashing and mandatory second-factor TOTP challenges.

2. Regulatory Compliance Mapping:

  • GDPR Article 25 (Privacy by Design): Data minimization restricts personal identity disclosure; students see only seat availability status, whereas names are restricted to authenticated librarians.
  • GDPR Article 32 (Security of Processing): End-to-end transport layer encryption (HTTPS/TLS) over port 443, private Docker bridge networks, and salted bcrypt cryptographic storage.
  • DPDPA 2023 (Digital Personal Data Protection Act - India): Clear purpose limitation for physical seat allocation and student right to record deletion upon university graduation.
